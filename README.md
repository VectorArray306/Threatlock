# Threatlock — local development prototype

A fictional conversation-security walkthrough. Requires Node 22.14+ (tested with 22.14).

```sh
npm install
npm run dev
npm test
npm run build
npm run test:e2e # run npx playwright install chromium first
```

Local mode uses no credentials, accounts, AWS resources, or external AI. All dependencies are bundled locally; local mode makes no runtime network requests. Drafts, fictional messages, rules, and incident metadata persist in this tab's sessionStorage. Reset the demo in How it Works.

## Behavior

- Eight curated scenarios with a Next message action, arbitrary typed fictional drafts, and a fixed attachment catalog. Recorded incoming signals are logged once when their exact conversation context is complete.
- Deterministic case-insensitive literal rules and restricted attachment classifications block sending. Up to 50 rules, 120 characters each. Rule edits are staged; preview checks the draft without publishing or logging an incident. Publish creates a global revision. Restore copies the previous published content into a new monotonically increasing revision.
- Recorded contextual results apply only to an exact scenario draft, conversation context, and attachment. Modified drafts say **Live AI is not connected** and can be sent explicitly without contextual analysis.
- Contextual warnings can be overridden. Blocks cannot. Manual escalation and metadata-only review are local operations.
- Each scenario conversation is limited to 200 messages; drafts to 2,000 characters. `cloudContext` bounds future cloud context to 20 messages / 16,000 characters.
- Repeated checks of an unchanged draft/context/published policy reuse a persisted assessment identity, so they do not duplicate incidents or overwrite their reviewed disposition.
- The dashboard stores opaque assessment IDs, fictional persona IDs, direction, reason codes, time, severity, risk, analysis source, optional attachment kind, and disposition. Conversation bodies never enter incident records.
- Live-session counts are separate from 12 explicitly seeded, read-only synthetic history events across three fictional personas. Hourly cells show count and highest severity; the severity distribution and persona filter reflect only the selected dataset.

## Adapter seam

`src/policy.ts` defines the request, result, attachment, rule, and incident contracts and the asynchronous `AnalysisAdapter`. `localAdapter` is an explicitly selected development adapter. The separate cloud presenter implementation below uses a strict API adapter and never selects this adapter or returns recorded fixtures.

The attachment catalog contains six bundled synthetic PNG/JPEG/single-page PDF files under 1 MB, generated by `generate-samples.py` (Pillow required only to regenerate). Assets can be previewed from the composer. OCR, uploads, authentication, cloud persistence and external AI are available only in the separate cloud mode after final account integration. Recorded screenshot analysis is explicitly fictional. This is a local prototype and is not a security product protecting real messaging apps.

## Offline AWS implementation

The AWS code is implemented locally. No stack has been deployed or connected to an account. Local commands explicitly select `VITE_APP_MODE=local`; `npm run dev:cloud` / `npm run build:cloud` select the separate cloud presenter UI. The cloud UI never imports recorded analysis or synthetic history into cloud records. Copy `.env.example` to `.env.local` and configure the stack outputs only during final account integration. A missing/invalid mode or cloud configuration fails visibly; it never falls back to local fixtures.

```sh
npm run typecheck:cloud
npm test
npm run synth -- --quiet # offline, --no-lookups; no account or credentials required
npm run build:cloud
```

`src/cloud-contract.ts` defines strict request shapes, sizes, identifiers and attachment provenance. `cloud/runtime.ts` handles authenticated assessments, staged/published policy revisions and metadata incident review. `cloud/aws.ts` provides real AWS SDK ports. `infra/stack.ts` defines Cognito with invitation-only presenters and required TOTP MFA, JWT-authorized HTTP API, Node 24 Lambda, pay-per-request DynamoDB, private S3 temporary uploads, Textract OCR, Ministral 3 8B contextual analysis, CloudWatch logs/metrics and a monthly Budget notification. Lambda uses Node 24; the local build toolchain was verified on Node 22.14.

The separate cloud screen supports sign-in, conversation context/draft entry, uploads attached to a specific context message or draft, checks, explicit warning/unscored overrides, blocked-send behavior, staged/published rules and incident review. It demonstrates sending inside this page; it does not send messages to other apps or protect Android applications. Authentication tokens stay in memory; the temporary PKCE verifier/state live in session storage until the OAuth callback. Ending the session also invokes Cognito logout. All authenticated presenters may publish the shared policy; invite only authorized demonstrators.

Cloud requests exclude fixture IDs, client classification, source, reason, persona and policy version. The server reads policy, derives ownership from verified JWT subject, verifies upload ownership/expiry/byte signatures/size, performs Textract OCR, and includes OCR with its message index in model context. Only PNG/JPEG/single-page PDF under 1 MB are supported; Textract rejects invalid/multipage documents. A restricted outgoing draft or draft attachment blocks before contextual AI. Incoming content informs contextual analysis without making an unrelated safe reply deterministic restricted content. An outgoing attachment that cannot be inspected blocks; unavailable incoming evidence or model service returns explicit unscored analysis. After each authenticated, validated assessment attempt, the server makes a best-effort deletion attempt for every referenced object whose server-owned metadata matches the presenter and upload ID. This includes outgoing text blocked before OCR and later attachments skipped after an early inspection exit or invalid reference. Cleanup failures do not change the assessment result and do not expose content. Invalid or unowned references never authorize deletion. S3 lifecycle is the fallback for failed cleanup, abandoned uploads, or interrupted Lambda execution: objects expire after at least one day, and actual deletion is asynchronous rather than immediate. Presigned forms expire after five minutes and enforce type/size; upload references expire after 15 minutes. Attachments are consumed by an assessment, so re-upload for a new check.

The server ignores free-form model explanations and returns generic descriptions. DynamoDB contains policy literals, upload ownership/expiry metadata and metadata-only incidents/assessment caches, never conversation bodies, OCR, attachment bytes or model explanations. Published policies are versioned, immutable revision rows plus a conditional current pointer. Publishing and incident/cache writes use transactions; repeated assessment IDs reuse metadata and reject changed requests. The server does not log events, prompts or model responses. Do not add request/body tracing or Lambda event logging. Provider processing of transient content (Textract/Bedrock) and region-specific retention/data handling need account-stage review. Incident listing shows the latest 100 for the signed-in presenter; no historical fixture data is inserted. DynamoDB TTL expires upload references and assessment caches asynchronously; incidents and policy history intentionally persist until account retention policy is configured.

API Gateway limits to 2 requests/second with burst 4, Lambda concurrency is 2, request bodies are capped at 30 KB, context at 20 messages/16,000 characters, draft at 2,000 characters, four attachments at 1 MB each, 50 literal rules and 300 model output tokens. API throttling and concurrency are protective bounds, not a guaranteed spend cap. A monthly USD 20 Budget sends an alert at 80%; AWS Budgets is delayed and **does not stop usage or guarantee zero payment**. DynamoDB PITR, retained data, logs, authentication, OCR and inference can incur charges. No cost guarantee is made. Final deployment requires explicit account-plan/free-credit/service-eligibility and pricing review. Retained tables/buckets/user pools require deliberate cleanup; destroying the stack alone does not remove them.

## Confirmed Mumbai model and pending account integration

The intended AWS Region is **ap-south-1 (Mumbai)** and the CDK app explicitly targets it. The user selected an **in-region model**: **Ministral 3 8B**, direct Bedrock model ID `mistral.ministral-3-8b-instruct`. It uses the regional Bedrock Runtime Converse API with the same server-side output validation and fail-to-unscored behavior. The 8B model was selected over 3B for the classification task at a small incremental demonstration cost; model accuracy still requires live evaluation. IAM invocation is restricted to the configured foundation model in Mumbai, with no cross-region inference profile grants.

The [AWS Bedrock model catalog](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html) lists the model and regional availability; confirm account access at integration. The researched Mumbai on-demand estimate is USD 0.18 per million input tokens and USD 0.18 per million output tokens; verify the current [Bedrock pricing](https://aws.amazon.com/bedrock/pricing/) and credit coverage before enabling it. Promotional credits are acceptable, while **zero out-of-pocket payment remains the intent**. The integration approval gate remains disabled until the actual account/service eligibility and cost review are complete.

Nova 2 Lite was considered and rejected for this Mumbai deployment because its [model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-amazon-nova-2-lite.html) requires GLOBAL cross-region inference from Mumbai. It is not the configured target or a fallback model.

The [limited “Sign up for AWS (new)” account experience](https://docs.aws.amazon.com/accounts/latest/reference/supported-services-sign-up-new.html) lists Textract only for its Paid Plan and restricts cross-region features in that account experience. Restrictions depend on the account signup path; verify that the actual account can use in-region Bedrock, Textract and the remaining stack services with eligible promotional credits. A credit balance and Budget alert do not guarantee no out-of-pocket charges. Do not enable deployment approval until the chosen account path satisfies the user's payment constraint.
